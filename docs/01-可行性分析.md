# MDPro3 本地 Rush Duel 人机对战 —— 可行性分析与落地方案

> 分析对象：MDPro3 / YGOMobile-cn-ko-en / ygopro-rush-duel / windbot
> 结论：**方向可行，架构上没有硬阻塞**，但有 3 个必须先对齐的事实（见 §0）。

---

## §0 结论先行：三个必须先说清楚的事实

### 事实 1：MDPro3 的"本地 AI"是 **WindBot（C#）**，牌组 AI 不是 Lua

MDPro3 把 WindBot 源码整个搬进了 Unity 工程：

```
Assets/Scripts/Windbot/Game/AI/Decks/*.cs      ← 每个牌组一个 C# executor
Assets/Scripts/Windbot/Game/AI/DefaultExecutor.cs
Data/Windbot/Decks/AI_*.ydk                    ← 每个 AI 牌组的卡表
Data/locales/<lang>/bot.conf                   ← 本地人机可选列表
```

所以"**新的牌组机器人可以根据 windbot 编写 lua**"这句需要修正：
- WindBot 的牌组 AI **是 C#**（`Game/AI/Decks/*.cs`），不是 Lua。
- Lua 在这套体系里只承担**卡片效果脚本**（`script/c<id>.lua`）的角色，由核心执行，跟机器人决策无关。
- WindBot 官方文档（`AGENTS.md`）明确写着"新增牌组 = 在 `Game/AI/Decks/` 加继承 `DefaultExecutor` 的执行器"。

### 事实 2：生态里**确实存在**一套 Lua AI —— 但 MDPro3 里是空壳

YGOPro Percy 原版客户端自带一套 Lua AI：

```
ygopro/ai/ai.lua          ← 主 AI 脚本（Snarky / Percival18）
ygopro/ai/ai-template.lua ← 写 AI 的模板 + API 文档
ygopro/ai/ai-cheating.lua
ygopro/ai/mod/*.lua       ← SelectCard / SelectChain / SelectSum / SelectTribute /
                            SelectPosition / SelectOption / SelectBattleCommand / DeclareCard ...
ygopro/ai/decks/*.lua     ← 每个牌组一个 Lua AI（ABC.lua / BLS.lua ...）
```

这套东西**才是"牌组 AI 用 Lua 写"**。你说的"这几个 ai 的 lua 我有"极可能指它。

但 MDPro3 里对应的入口是**空的**：

```csharp
// Assets/Scripts/MDPro3/Duel/PercyOCG.cs
public void StartAI()
{
    //Program.instance.ocgcore.handler = Response;   ← 被注释掉了
}
```

MDPro3 只把 Percy 的 `ocgcore` 原生库用于**残局（Puzzle）和回放**，没接 AI。

### 事实 3：Rush Duel 是"数据扩展 + 一条全局规则脚本"，**没有模式开关**

RD 规则通过 `special.lua` 触发，而内置服务器**在服务器模式下无条件加载它**。也就是说：
- 只要本地脚本搜索路径里存在 RD 的 `special.lua`，**这一局的规则就是 RD**；
- 想同时保留普通模式，需要额外做**模式隔离**（见 §6 阶段 2）。

## §1 四个仓库的真实分工

| 仓库 | 本质 | 关键内容 | 有没有 AI |
|---|---|---|---|
| **MDPro3** | Unity 客户端（全栈） | 客户端 + 内置 `ocgcore.dll` + 内置 `ygoserver.dll` + 内置 WindBot(C#) + YGOSharp 协议层 | ✅ 内置 WindBot |
| **YGOMobile-cn-ko-en** | Android 客户端 | Java + NDK；核心以预编译 `libYGOMobile.so` / `libWindbot.aar` 引入 | ✅ 用 `libWindbot.aar` |
| **ygopro-rush-duel** | **纯数据扩展** | `RD Standard/Alternate/Patch.cdb` + `script/` 3086 个 lua + `lflist.conf` + `strings.conf` + `sets.md` | ❌ 无 AI、无核心改动 |
| **windbot** | C# 决斗机器人 | 协议层客户端 + 73 个牌组 executor | ✅ 本体就是 AI |

**关键认知**：`ygopro-rush-duel` 不包含任何 AI，也不改核心。它只是"塞进服务器 `expansions/` 目录的数据包"。所以"RD 模式"能不能跑，取决于**核心+服务器**，而不是这个仓库。

MDPro3 的技术栈（证据）：
```
Tools/YGO Classes/ocgcore/      ← C++ 核心源码（含 duel/interpreter/libduel/field ...）
Tools/YGO Classes/ygoserver/    ← C++ 服务器源码（single_duel.cpp / game.cpp / data_manager.cpp）
Assets/Plugins/Windows/         ← ocgcore.dll / ygoserver.dll / sqlite3.dll
Assets/Scripts/Windbot/         ← 内置 WindBot（C#，与 IceYGO/windbot 同构）
Assets/Scripts/YGOSharp/        ← 协议层（CtosMessage / StocMessage / GameMessage）
Assets/Scripts/MDPro3/Duel/CoreWrapper.cs  ← Percy 命名空间，P/Invoke 直连 ocgcore
```

## §2 MDPro3 的"本地人机"到底是怎么跑起来的

入口：`Assets/Scripts/MDPro3/Servant/SoloSelector.cs`

```csharp
private void LaunchWithConfig(string command, int duelPort, int duelLp, int duelHand, int duelDraw, ...)
{
    port = duelPort.ToString();
    string args = port + " -1 5 0 F " + (noCheck ? "T " : "F ") + (noShuffle ? "T " : "F ")
                + lp + " " + hand + " " + draw + " 0 0";
    if (TcpHelper.IsPortAvailable(duelPort))
    {
        YgoServer.StartServer(args);                 // ① 进程内启动 YGOPro 服务器
        TcpHelper.LinkStart("127.0.0.1", ..., port, string.Empty, true,
            () => StartWindBot(command, "127.0.0.1", port, ...));  // ② 玩家连本地
    }
}

public void StartWindBot(string command, string ip, string port, string password, bool lockHand, int delay)
{
    // ... 拼装 Name=/Deck=/Dialog=/Host=/Port= 参数 ...
    (new Thread(() => { Thread.Sleep(delay); WindBot.Program.Main(args); })).Start();  // ③ 进程内起 WindBot
}
```

**所以"本地人机"= 内置服务器 + 内置 WindBot，走 127.0.0.1 本地 TCP。**
它和"连远程服务器加 AI"是**同一套协议模型**，区别只是 host 是本地还是远程、WindBot 是进程内还是独立进程。

启动参数已被我逐位对照 `ygoserver/gframe.cpp` 解析确认：

| 位置 | 值 | 含义 |
|---|---|---|
| argv[1] | port | 端口 |
| argv[2] | -1 | lflist（<0 → 999，即不限） |
| argv[3] | 5 | **rule（0-5）**：3=大师规则3，4=新大师规则，**5=大师规则2020** |
| argv[4] | 0 | mode（0=单打，1/2=其他） |
| argv[5] | F | 大师规则开关 |
| argv[6]/[7] | F F | noCheckDeck / noShuffleDeck |
| argv[8..10] | lp/hand/draw | 起始 LP / 初始手牌 / 抽卡数 |
| argv[11]/[12] | 0 0 | 时间限制 / 回放模式 |

> ⚠️ 注意：`rule=5` 是**大师规则选择**，**不是** RD 开关。本地服务器**没有任何"Rush Duel"参数**。

WindBot 侧的对接点：
- `bot.conf` → `SoloSelector.ReadBots()` 解析（`!名称 / 命令 / 描述 / flags`）
- 牌组 .ydk → `Data/Windbot/Decks/AI_*.ydk`
- 决策 → `Game/GameAI.cs` 按 `Executor.Executors` 注册顺序匹配

## §3 Rush Duel 是怎么实现的（这是可行性的核心）

### 3.1 规则全在 Lua，靠全局效果改规则

入口 `script/special.lua`：

```lua
Duel.LoadScript("RDBase.lua")
Duel.LoadScript("RDRule.lua")
Duel.LoadScript("RDMaximum.lua")
Duel.LoadScript("RDFusion.lua")
Duel.LoadScript("RDRitual.lua")
-- ... 共 18 个 RD*.lua
RD = RushDuel
function Auxiliary.PreloadUds()
    RD.Init()
end
```

`script/RDRule.lua` 用**全局效果**改规则：

| RD 规则 | 实现 |
|---|---|
| 召唤次数无限制 | `EFFECT_SET_SUMMON_COUNT_LIMIT = 100` |
| 抽卡阶段抽到 5 张 | `EFFECT_DRAW_COUNT` = `max(1, 5 - 手牌数)` |
| 先攻也抽 1 张 | `EVENT_PHASE_START + PHASE_DRAW` 里 `Duel.Draw(0,1,REASON_RULE)` |
| 无准备阶段 / 无主要阶段 2 | `EFFECT_SKIP_SP` / `EFFECT_SKIP_M2` |
| 手牌无上限 | `EFFECT_HAND_LIMIT = 100` |
| 场上怪兽效果强制 1 回合 1 次 | `EFFECT_CANNOT_ACTIVATE` + `EVENT_CHAIN_SOLVING` 打 flag |
| 同一时点只能发动 1 张陷阱 | `EVENT_CHAINING` + `Duel.SetChainLimit` |
| 禁用最左/最右列 | `EFFECT_DISABLE_FIELD = 0x11711171` |
| 极大（Maximum） | `RDMaximum.lua`：`TYPE_MAXIMUM` + `AddHandSpecialSummonProcedure` |
| 传说卡 | `RDLegend.lua` + `lflist.conf` 的 `$legend_monster/spell/trap` |

### 3.2 触发点：服务器在"服务器模式"下**无条件**加载 special.lua

`Tools/YGO Classes/ygoserver/single_duel.cpp:578`

```cpp
#ifdef YGOPRO_SERVER_MODE
	preload_script(pduel, "./script/special.lua");
#endif
```

脚本解析顺序（`ygoserver/data_manager.cpp: ScriptReaderEx`）：

```
"./script/xxx.lua"
  → specials/xxx.lua        （pre_len=9，优先）
  → expansions/script/xxx.lua
  → script/xxx.lua          （默认）
```

卡库加载（`ygoserver/game.cpp: LoadExpansions`）：`./cdb/*.cdb` → `./Data/locales/zh-CN/*.cdb` → `./expansions/*.cdb`

**推论**：把 RD 扩展按 `expansions/*.cdb` + `expansions/script/*.lua` + `expansions/*.conf` 摆好，内置服务器就会进入 RD。这正是 `ygopro-rush-duel` 的 CI 打包布局（`mv *.cdb expansions/; mv script expansions/`）。

### 3.3 RD 的所有"选择"都走**标准协议消息** ← 这是可行性的关键

RD 自定义了 `RushDuel.Select(...)`，但它底层是：

```lua
-- script/RDFunction.lua
function RushDuel.Select(hint, player, group, check, cancelable, min, max, ...)
    Duel.Hint(HINT_SELECTMSG, player, hint)
    if check == nil then
        return cancelable and group:CancelableSelect(player, min, max, nil)
                         or  group:Select(player, min, max, nil)
    else
        return group:SelectSubGroup(player, check, cancelable, min, max, ...)
    end
end
```

→ 落到 ocgcore 的标准 API → 产生标准 `MSG_SELECT_CARD` / `MSG_SELECT_UNSELECT_CARD` / `MSG_SELECT_SUM`。

WindBot 已有对应的通用处理：

```
Game/GameBehavior.cs
  OnSelectCard()          ← MSG_SELECT_CARD
  OnSelectSum()           ← MSG_SELECT_SUM（融合/仪式/极大素材都走这里）
  OnSelectUnselectCard()  ← SelectSubGroup 的多步选择
  OnSelectIdleCmd()       ← 主要阶段动作（多次召唤就是多次收到这个）
  OnSelectYesNo() / OnSelectOption() / OnSelectPosition() / OnSelectTribute() ...

Game/AI/Executor.cs（虚方法）
  OnSelectSum / OnSelectFusionMaterial / OnSelectRitualTribute / OnSelectTribute ...
```

**结论：机器人不需要理解 RD 规则，核心已经理解了；机器人只需要"看到提示、做决策"。协议层天然兼容。**

## §4 两套 AI 体系对照

| | **WindBot（C#）** | **YGOPro Percy Lua AI** |
|---|---|---|
| 语言 | C# | Lua |
| 位置 | 独立进程 / MDPro3 进程内 | 客户端进程内（原版 ygopro） |
| 通信 | YGOPro 网络协议（TCP） | 直接回调，无网络 |
| 牌组 AI | `Game/AI/Decks/*.cs` | `ai/decks/*.lua` |
| 通用决策 | `DefaultExecutor.cs` / `GameAI.cs` | `ai/mod/*.lua` |
| MDPro3 支持 | ✅ 完整接入（SoloSelector） | ⚠️ 仅空壳（`PercyOCG.StartAI()` 被注释） |
| YGOMobile 支持 | ✅ `libWindbot.aar` | ❌ 未集成 |
| 与 RD 的适配 | 需要新写 RD 牌组 executor | 需要先"接线"再做 RD 牌组 AI |
| 工作量 | 中（有现成脚手架） | 大（要先补客户端集成） |

## §5 可行性逐项判断

| 环节 | 判断 | 依据 |
|---|---|---|
| RD 规则在本地生效 | ✅ 可行 | 服务器无条件加载 `special.lua`，只要扩展在 `expansions/` |
| RD 卡牌能显示 | ✅ 已具备 | `CardBuilderRushDuel.cs`、`Assets/Texture/CardFrames/RushDuel` |
| 机器人能参与 RD 对局 | ✅ 可行 | RD 走标准协议消息，WindBot 有 `OnSelectSum` 等通用回调 |
| 机器人能"打好"RD | ⚠️ 需开发 | 需新写 RD 牌组 executor + .ydk + bot.conf |
| 本地同时保留普通模式 | ⚠️ 需改造 | 无模式开关，`special.lua` 全局生效，需做隔离 |
| 复用你说的"ai 的 lua" | ❓ 待确认 | 若指 Percy Lua AI，MDPro3 需先补 `StartAI()` 接线 |
| YGOMobile 侧 | ⚠️ 成本高 | 需 NDK 重编核心 + 重打包 APK，且同样无 RD 模式开关 |

**总体：方案成立。** 最大的不确定性不在"能不能"，而在"用哪套 AI 引擎"和"要不要模式隔离"。

## §6 建议的落地方案（分阶段）

### 阶段 0：链路验证（不写 AI，先证明规则能通）
1. 把 RD 扩展按服务器布局放到 MDPro3 数据根：
   ```
   Expansions/RD Standard.cdb
   Expansions/RD Alternate.cdb
   Expansions/RD Patch.cdb
   Expansions/lflist.conf
   Expansions/strings.conf
   Expansions/script/*.lua        （含 special.lua + RD*.lua + c*120*.lua）
   ```
2. 启动本地人机，随便选一个现有 bot。
3. **预期**：规则变成 RD（抽到 5 张、可多次召唤、无主要阶段 2），但 bot 会乱打（它的 .ydk 是 OCG 卡，不在 RD 卡池里）。
4. 只要第 3 步的"规则变了"成立 → 链路打通，剩下都是 AI 的事。

### 阶段 1：最小可用 RD 牌组 AI
1. 参考 WindBot 里最"通用"的执行器：`Game/AI/Decks/DoEveryThingExecutor.cs`、`LuckyExecutor.cs`（兜底策略），或 `MokeyMokeyExecutor.cs`（极简）。
2. 新建 `Assets/Scripts/Windbot/Game/AI/Decks/RdXxxExecutor.cs`：
   - 用 `[Deck("RD-XXX", "AI_RdXxx")]` 注册
   - 卡号用 RD 卡号（12xxxxxxx 段）
   - 实现 `AddExecutor` 优先级：召唤 → 融合/极大 → 效果 → 攻击
3. 配 `Data/Windbot/Decks/AI_RdXxx.ydk`
4. 在 `Data/locales/zh-CN/bot.conf` 加条目（带 `SUPPORT_MASTER_RULE_2020` 之类的 flag）
5. 重新编译 Unity 工程验证

### 阶段 2：模式隔离（让普通/RD 共存）
三个选项，按侵入性排序：
- **(a) 目录切换（最轻）**：RD 模式启动前把 RD 的 `special.lua`+`RD*.lua` 拷进 `specials/`，普通模式启动前清掉。只改 C#，不动 C++。
- **(b) 启动参数（中等）**：给 `ygoserver` 增加一个 mode 参数，控制是否 `preload_script("special.lua")`。需要重编 `ygoserver.dll`（`Tools/YGO Classes` 里有完整源码 + premake，可行）。
- **(c) 双数据根（最稳）**：维护两套 `Expansions/` 状态，由启动器切换。

### 阶段 3：牌组 AI 库 + 调优
- 按 RD 主流牌组（七星道、青眼、真红眼、银河、连击龙…）逐个写 executor
- 处理 RD 特有决策：多次召唤顺序、极大召唤时机、传说卡、RD 融合素材

### 备选路线：接 Percy Lua AI
若你手上的"lua"确实是 `ai/decks/*.lua`：
- 需要先把 `PercyOCG.StartAI()` 接线（MDPro3 已有 `Percy.Ygopro` + `ocgcore.dll`）
- 然后确认 Percy 的 AI 驱动逻辑是在**客户端**还是**核心**里（原版 ygopro 是在客户端里驱动 `ai.lua`，MDPro3 只搬了核心）
- 这条路工作量更大，但能**直接复用你已有的 Lua AI**

## §7 风险清单

| 风险 | 说明 | 缓解 |
|---|---|---|
| `special.lua` 全局生效 | 装 RD 扩展后普通本地人机也会变 RD | 阶段 2 做隔离 |
| WindBot 内置版与上游可能分叉 | MDPro3 的 Windbot 是拷贝，README 说 `bot.conf` 从 YGOMobile 同步 | 改 AI 时以 MDPro3 内那份为准 |
| RD 特有交互 | 极大召唤的"3 只选 2"、RD 融合/仪式素材顺序 | 用 `OnSelectSum`/`OnSelectCard` 显式处理 |
| WindBot 架构局限 | 无法预演卡片脚本，`AI.Select*` 是"预先选择"，多段连锁可能错位（见其 `AGENTS.md`） | RD 卡效果更简单，风险低于 OCG |
| 需重编 Unity 工程 | 改 C# 要 Unity 6000.0.10f1 环境 | 提前准备构建环境 |
| YGOMobile 侧 | NDK R29 重编核心 + 签名/包名 | 若只在 MDPro3 落地可暂不碰 |

## §8 需要你确认的问题

1. **"这几个 ai 的 lua"具体是哪一套？**
   - (a) YGOPro Percy 的 `ai/ai.lua` + `ai/decks/*.lua`（客户端内置 Lua AI）
   - (b) 服务器上 windbot 的配置/牌组
   - (c) 别的
   → 把文件发我，我一眼就能分辨。

2. **你平时在 MDPro3 里是怎么打 RD 的？**
   - 连 `rd.mycard.moe` 之类的服务器？
   - 还是本地已经装了 RD 扩展？
   → 这决定了阶段 0 的起点。

3. **要不要保留普通模式？**
   → 决定走阶段 2 的 (a) 还是 (b)/(c)。

4. **落地目标客户端**：只在 MDPro3（Windows），还是也要 YGOMobile（Android）？
